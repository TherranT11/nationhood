CIVIC — Revised Implementation Plan
Adapted from Design Guide v3.0 to match Nationhood codebase
========================================================================

SUMMARY OF CHANGES FROM ORIGINAL GUIDE
---------------------------------------
The original guide assumed: standalone Events.html, local gameState with
save/load, client-side function hooks (47 civicFireEvent calls), and a
single-page app. The actual codebase is: multi-page Vite app, Supabase
backend, events tab inside politics.html, server-side tick processing
via edge functions, and two existing event tables (event_log +
campaign_actions).

This plan adapts CIVIC to work WITH the existing architecture instead of
against it.


========================================================================
ARCHITECTURE DECISION: PULL MODEL (not Push)
========================================================================

The original guide uses a PUSH model: inject civicFireEvent() into 47
game functions. This is unworkable because:

  1. Most game events fire server-side in supabase/functions/advance-tick/
     index.ts — client JS cannot inject hooks there.
  2. Events already write to two Supabase tables:
     - event_log (system events: bills, crises, elections, trade, etc.)
     - campaign_actions (faction actions: rally, outreach, attack, etc.)
  3. Modifying 47 server functions is fragile and high-risk.

REVISED APPROACH: CIVIC reads from event_log and campaign_actions, then
transforms those rows into styled CIVIC posts using the v3.0 templates.
Player posts go to a new civic_posts table in Supabase.

  event_log row  -->  template lookup  -->  CIVIC post object  -->  render
  campaign_action  -->  template lookup  -->  CIVIC post object  -->  render
  player input  -->  civic_posts insert  -->  CIVIC post object  -->  render


========================================================================
FILE STRUCTURE (revised)
========================================================================

  css/civic.css              -- CIVIC styles, CSS variables, tag colors
  js/civic.js                -- core logic: render, compose, threads, queue
  js/civic-handles.js        -- 20-entry handle pool (unchanged from guide)
  js/civic-templates.js      -- event templates + mapping from event_log
                                trigger keys to template sets

  politics.html              -- add <link> to civic.css, add <script> tags
                                for civic-handles.js, civic-templates.js,
                                civic.js. Modify Events tab container.

  sql/migrations/YYYYMMDD_create_civic_posts.sql

NO standalone Events.html. NO events/ subdirectory.

PHASE 1: DATABASE — civic_posts table
========================================================================

Create a Supabase migration:

  CREATE TABLE civic_posts (
    id            uuid DEFAULT gen_random_uuid() PRIMARY KEY,
    nation_id     uuid NOT NULL REFERENCES nations(id),
    faction_id    uuid REFERENCES factions(id),  -- null for system posts
    handle_key    text NOT NULL,                  -- e.g. '@freepress_vald'
    display_name  text NOT NULL,
    initials      text NOT NULL,
    body          text NOT NULL CHECK (char_length(body) <= 280),
    created_at    timestamptz DEFAULT now(),
    game_tick     int NOT NULL,
    likes         int DEFAULT 0,
    shares        int DEFAULT 0,
    liked_by      uuid[] DEFAULT '{}',
    shared_by     uuid[] DEFAULT '{}',
    created_at_ts timestamptz DEFAULT now()
  );

  CREATE TABLE civic_comments (
    id            uuid DEFAULT gen_random_uuid() PRIMARY KEY,
    post_id       uuid NOT NULL REFERENCES civic_posts(id) ON DELETE CASCADE,
    nation_id     uuid NOT NULL,
    faction_id    uuid REFERENCES factions(id),
    handle_key    text NOT NULL,
    display_name  text NOT NULL,
    initials      text NOT NULL,
    body          text NOT NULL CHECK (char_length(body) <= 280),
    game_tick     int NOT NULL,
    created_at    timestamptz DEFAULT now()
  );

  -- RLS: players can read all posts for their nation, insert their own
  ALTER TABLE civic_posts ENABLE ROW LEVEL SECURITY;
  CREATE POLICY civic_posts_read ON civic_posts FOR SELECT
    USING (nation_id IN (SELECT nation_id FROM factions WHERE id = auth.uid()));
  CREATE POLICY civic_posts_insert ON civic_posts FOR INSERT
    WITH CHECK (faction_id = auth.uid());

  -- Same for comments
  ALTER TABLE civic_comments ENABLE ROW LEVEL SECURITY;
  CREATE POLICY civic_comments_read ON civic_comments FOR SELECT
    USING (nation_id IN (SELECT nation_id FROM factions WHERE id = auth.uid()));
  CREATE POLICY civic_comments_insert ON civic_comments FOR INSERT
    WITH CHECK (faction_id = auth.uid());

NOTE: System-generated posts (from event_log) are NOT stored in
civic_posts. They are generated client-side from event_log rows on each
render. Only player-authored posts persist in civic_posts.

ALTERNATIVE: If you want system posts to also persist (so likes/shares
on system posts survive page reloads), insert them into civic_posts with
faction_id = null during advance-tick processing. This is cleaner but
requires a server-side change. Decide before implementing.

PHASE 4: civic-templates.js — EVENT MAPPING
========================================================================

This is the critical adaptation layer. The guide's 47 event types must
be mapped to the actual trigger keys in event_log and action types in
campaign_actions.

Structure:

  const CIVIC_EVENT_MAP = {
    // event_log trigger keys -> CIVIC template key
    'bill_passed':                    'bill_passed',
    'bill_failed':                    'bill_failed',
    'quorum_failed':                  'bill_failed',  // reuse bill_failed templates
    'presidential_election':          'presidential_election',
    'formation_snap_election':        'snap_election',
    'emergency_minority_government':  'minority_government',
    'trade_agreement_expired':        'trade_agreement_rejected',
    'aid_terminated':                 'trade_agreement_rejected',
    'aid_suspended':                  'crisis_start',
    'aid_resumed':                    'trade_agreement_accepted',
    'pm_appointed':                   'minister_appointed',
    'incumbent_lockin':               'presidential_election',
    // ... map all known trigger keys
  };

  const CIVIC_ACTION_MAP = {
    // campaign_actions action_types -> CIVIC template key
    'rally':                          'party_action',
    'outreach':                       'party_action',
    'attack':                         'faction_action',
    'buy_influence':                  'faction_influence',
    'faction_buy_influence':          'faction_influence',
    'intimidate':                     'faction_action',
    'purge':                          'faction_action',
    'coup_success':                   'coup_succeeded',
    'coup_failed':                    'coup_failed',
    'party_disbanded':                'party_dissolved',
    'faction_consolidate_power':      'strongman_power',
    // ... map all known action types
  };

Each template set is exactly as written in guide Section 6 (all 47 sets,
5 templates each). The mapping layer translates real DB records into the
correct template set.

VARIABLE EXTRACTION: Each mapping also needs a variable extractor that
pulls template variables from the event_log/campaign_actions row:

  const CIVIC_VAR_EXTRACTORS = {
    'bill_passed': (row) => ({
      bill_name: row.effects_applied?.bill_name || row.event_name || 'Unknown Bill',
      votes_for: row.effects_applied?.votes_for || '?',
      votes_against: row.effects_applied?.votes_against || '?',
      margin: Math.abs((row.effects_applied?.votes_for||0) - (row.effects_applied?.votes_against||0)),
    }),
    'party_action': (row) => ({
      party: row.result?.faction_name || row.factions?.faction_name || 'Unknown',
      action: row.action_type?.replace(/_/g, ' ') || 'action',
      issue: row.result?.issue || '',
      region: row.result?.region || '',
    }),
    // ... one per template set
  };

UNMAPPED EVENTS: Some of the guide's 47 events do not currently fire in
the codebase. These template sets should still be written (they're good
content) but will only activate when the game adds those features:

  - state_visit_proposed/accepted/happened/rejected (no state visit
    system exists yet — diplomacy uses proposals, not visits)
  - diplomatic_initiative_proposed/accepted/rejected (partially exists
    via diplomatic_proposals table but no client-side trigger keys)
  - bill_proposed (bills go straight to committee, no "proposed" event)
  - bill_amended, filibuster_called (not implemented)
  - nation_joins_org, nation_leaves_org (no IO membership system)
  - io_charter_amended, io_cohesion_collapsed (not implemented)
  - party_founded (no party creation system — factions are fixed)
  - party_kicked_coalition (coalition kicks not a distinct event)
  - presidential_endorsement (endorsements exist but no event_log entry)
  - corporate_contract_signed (no corporate system)
  - minister_nomination_rejected (exists but may not fire event_log)
  - executive_order_issued/expired (EOs exist but may not fire event_log)
  - overreach_threshold, regime_health_threshold (thresholds fire to
    campaign_actions, need mapping)
  - consolidation_begins (no distinct event — inferred from regime health)

RECOMMENDATION: Implement templates for all 47 but map only the ~25
that have real trigger keys today. The rest activate automatically when
their trigger keys appear in event_log. No dead code, no wasted work.

5.1  INITIALIZATION
--------------------
Called when the Events tab is activated in politics.html.

  async function initCivic(supabase, nationId, factionId, currentTick) {
    // Fetch data sources in parallel
    const [eventLogRows, campaignRows, playerPosts] = await Promise.all([
      supabase.from('event_log')
        .select('*')
        .eq('nation_id', nationId)
        .order('fired_at_tick', { ascending: false })
        .limit(80),
      supabase.from('campaign_actions')
        .select('*, factions(faction_name, abbreviation, party_color)')
        .eq('nation_id', nationId)
        .order('tick_performed', { ascending: false })
        .limit(80),
      supabase.from('civic_posts')
        .select('*, civic_comments(*)')
        .eq('nation_id', nationId)
        .order('created_at', { ascending: false })
        .limit(100),
    ]);

    // Transform event_log + campaign_actions into CIVIC post objects
    const systemPosts = transformToCivicPosts(eventLogRows.data, campaignRows.data, currentTick);

    // Merge with player posts, sort by game_tick desc, cap at 100
    const allPosts = mergeAndSort(systemPosts, playerPosts.data);

    // Render
    renderCivicFeed(allPosts);
    renderTrending(allPosts);
  }

5.2  TRANSFORM FUNCTION
------------------------
  function transformToCivicPosts(eventRows, actionRows, currentTick) {
    const posts = [];

    // Process event_log rows
    for (const row of (eventRows || [])) {
      const triggerKey = extractTriggerKey(row);  // parse from event_name
      const templateKey = CIVIC_EVENT_MAP[triggerKey];
      if (!templateKey) continue;  // no template for this event type

      const templates = CIVIC_TEMPLATES[templateKey];
      if (!templates?.length) continue;

      const vars = CIVIC_VAR_EXTRACTORS[templateKey]?.(row) || {};
      const picked = pickNoReplace(templates, 2);  // 2 posts per event

      for (const tmpl of picked) {
        const body = fillTemplate(tmpl.text, vars);
        if (/\{\w+\}/.test(body)) continue;  // skip if variables unfilled
        const handle = pickNoReplace(CIVIC_HANDLES, 1)[0];

        posts.push({
          id: 'sys_' + row.id + '_' + tmpl.id,
          type: 'system',
          name: handle.name,
          initials: handle.initials,
          handle: handle.handle,
          body: body,
          date: tickToDate(row.fired_at_tick),
          tick: row.fired_at_tick,
          eventTag: tmpl.eventTag,
          likes: Math.floor(Math.random() * 40) + 3,   // cosmetic seed
          shares: Math.floor(Math.random() * 15),        // cosmetic seed
          likedByPlayer: false,
          sharedByPlayer: false,
          comments: [],
          open: false,
        });
      }
    }

    // Process campaign_actions rows (similar logic using CIVIC_ACTION_MAP)
    // ...

    return posts;
  }

NOTE: System post likes/shares are seeded randomly on each render.
They are cosmetic and do not persist. If persistence is desired, use
the civic_posts table approach (Phase 1 alternative).

DETERMINISTIC HANDLES: Because system posts regenerate on each page
load, the handle assigned to a given event will change each time.
To make handles stable, seed the random picker with the event row ID:

  function seededRandom(seed) {
    // Simple hash-based PRNG from row UUID
    let h = 0;
    for (let i = 0; i < seed.length; i++) {
      h = ((h << 5) - h) + seed.charCodeAt(i);
      h |= 0;
    }
    return Math.abs(h);
  }
  const handleIndex = seededRandom(row.id) % CIVIC_HANDLES.length;

    const { error } = await _supabase.from('civic_posts').insert({
      nation_id: gameState.nation.id,
      faction_id: gameState.faction.id,

      initials: handle.initials,

  }

    async function updateCivicBadge(faction, nation) {
      const badge = document.getElementById('civic-badge');
      if (!badge || !faction || !nation) return;
      const lastSeenTick = parseInt(
        localStorage.getItem('civic_last_seen_tick_' + nation.id) || '0'

RISK REGISTER
========================================================================

1. TEMPLATE COVERAGE GAP
   Only ~25 of 47 event types have trigger keys in event_log today.
   The remaining templates sit dormant until those features ship.
   MITIGATION: This is fine. Templates are cheap. They activate
   automatically when trigger keys appear.

2. VARIABLE EXTRACTION FRAGILITY
   event_log rows store data in effects_applied (JSONB) with
   inconsistent key names across different event types.
   MITIGATION: Write extractors defensively with fallbacks.
   Test each extractor against real event_log rows.

3. SYSTEM POST NON-PERSISTENCE
   Likes/shares/comments on system posts don't survive page reload
   in v1 (pull model generates fresh posts each time).
   MITIGATION: Acceptable for v1. If it bothers users, add server-
   side materialization in v2.

4. HANDLE STABILITY
   System posts get different random handles on each page load.
   MITIGATION: Use seeded PRNG based on row UUID (see Phase 5.2).

5. PERFORMANCE
   Fetching 80 event_log + 80 campaign_actions + 100 civic_posts
   on every tab open could be slow.
   MITIGATION: Cache in sessionStorage with 2-minute TTL. Only
   refresh on explicit pull-to-refresh or tab re-entry after 2min.

6. MULTI-PAGE BADGE STALENESS
   Badge count is calculated on page load. If events fire while
   the player is on the page, badge won't update until next
   navigation.
   MITIGATION: Acceptable. Same behavior as existing bills/diplomacy
   badges. Could add Supabase realtime subscription later.
